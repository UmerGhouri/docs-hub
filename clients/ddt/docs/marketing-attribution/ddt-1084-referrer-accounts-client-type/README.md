## 1. Summary

Every new Account was stamped "Potential Defense Client" by the client-type trigger, whatever it was. Once DDT-862 let staff create referrers inline, medical practices and business partners were being labelled as potential clients too, and anything keyed on client type (routing, outreach, messaging sync, reporting) treated them as such. The classification now clears the type on medical provider, insurance carrier, vendor and repair facility Accounts, and on referrers created from the referral picker. 577 existing rows were cleaned up.

## 2. What was reported

- 2026-09-15 (named when DDT-862 closed), filed 2026-09-22: `ClientTypeTrigger` stamps every new Account as Potential Defense Client regardless of source, and the referral panel cannot work around it.

## 3. Scope

**In scope**

- `ClientTypeTriggerService` and `ClientTypeTriggerTest`.
- `ReferralSourceController.createReferrer` and `ReferralSourceControllerTest`.
- A one-off no-change re-save of existing non-client Accounts carrying the wrong type.

**Out of scope**

- Business Accounts: deliberately still classified, because 10 past defense clients and 1 active defense client are business accounts.
- Inbound-call Leads defaulting to Defense: DDT-1135.

## 4. How it works (background)

`ClientTypeTrigger` runs `ClientTypeTriggerService` on Account save, which works out `Primary_Client_Type__c` through a chain of rules. With no case history, the chain fell through to "Potential Defense Client". Referrers created from the picker are Accounts (providers, partners) or Person Accounts (previous clients, friends and family).

## 5. Root cause

The classification chain had no notion of an Account that is not a client at all: every record type went through the same default. Measured after the fix: 463 Medical Provider, 85 Insurance Carrier and 29 Vendor Accounts read "Potential Defense Client".

## 6. Solution

1. Before the classification chain runs, the service clears `Primary_Client_Type__c` on Accounts with record type Medical Providers, Insurance Carrier, Vendor or Repair Facility. Cleared rather than skipped, so a wrongly stamped row heals on its next save.
2. `createReferrer` sets a flag around its own insert so a Business Partner referrer is not classified either. Why a flag: Business Account is not in the skip list because some real clients are business accounts, so a business partner referrer needs its own signal from the code that creates it.
3. One existing test had pinned the old behaviour (expecting "Potential Defense Client"); it now expects no type and cites this ticket.
4. Backfill: the before-state (Id, record type, old type) of all 577 rows was saved first, then one no-change update with partial success.

## 7. Testing

- Validation with `ClientTypeTriggerTest` and `ReferralSourceControllerTest`: 27 tests, 0 failures. Re-run against the deployed code: 28 of 28, including five guard tests and a regression test that business-account clients keep their type.
- One sandbox-only failure (`testActivePI`) also fails on the unchanged code there and passes in production; not related.
- Backfill: 577 attempted, 577 succeeded, 0 failed, including 56 owned by inactive users. After: 463 Medical Providers, 85 Insurance Carriers and 30 Vendors, all with an empty type (the before count said 29 vendors and the after count 30; the ticket does not explain the difference). No tasks or emails were generated by the re-save.
- First real proof: a vendor Account created by staff shortly after the deploy never received a type. Person Accounts saved after the deploy kept their types.

## 8. Step by step

1. Read the production copy of the classification code and find the default branch.
2. Decide which record types are never clients, and which need an explicit signal from the creating code.
3. Clear the value for non-clients before the chain runs, so old rows heal on save.
4. Update tests that pinned the old behaviour, and add a regression test for the clients you must keep.
5. Export the before-state, then re-save the affected rows with partial success.
6. Warn anyone whose list view or report is keyed on the old value.

## 9. Rollback

Redeploy the previous versions of the four classes. The deploy changed no data; the backfill's before-state export allows the old values to be restored if ever needed.

## 10. Known limits

- Any list view, report or outreach filter keyed on "Potential Defense Client" lost those 577 rows at once. That is the correct result, but visible.
- Business Account referrers are only protected when created through the referral picker; one created another way is still classified.

## 11. Reuse for similar issues

- Signs of the same problem: non-client Accounts (vendors, providers, insurers) showing up in client lists or outreach.
- Clear a derived value rather than skipping it, so bad history fixes itself on the next save.
- When record type cannot distinguish two cases, let the creating code pass an explicit signal.
- Save the before-state of every row before a bulk re-save.
