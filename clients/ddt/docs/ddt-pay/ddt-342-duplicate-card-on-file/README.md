## 1. Summary

When staff entered a card that a client already had on file, DDT Pay saved a second card-on-file record for it. The duplicate check only compared the payment processor's stored-card reference, and the processor returns a new reference each time the same card is added. The check now also matches on the client account, card brand and last four digits, and keeps a single card-on-file pointing at the newest processor reference. Verified in the Partial Copy sandbox; not yet in production.

## 2. What was reported

- 2026-07-15: from the sandbox test pass (A4): re-entering a card already on file created a duplicate card-on-file.

## 3. Scope

**In scope:** the card-on-file duplicate check in `PayStaffActionsController`, and `PayStaffActionsControllerTest`.

**Out of scope:** how card details are entered and stored. That is handled by the payment processor and was not changed.

## 4. How it works (background)

When a card is saved for a client, the payment processor (Authorize.Net) keeps the card and returns a reference to it. Salesforce stores a card-on-file record with that reference (`Payment_Profile_Id__c`) plus display details: `Card_Brand__c` and `Card_Last_Four__c`. Staff and autopay charge the card through that reference.

## 5. Root cause

The processor issues a new reference every time the same card is saved again, so the Salesforce check, which matched only on `Payment_Profile_Id__c`, never saw a match. This was confirmed in sandbox data: one account had two card-on-file records for the same card brand and last four digits (ticket description).

## 6. Solution

The duplicate check now also matches on Account + `Card_Brand__c` + `Card_Last_Four__c`. When it finds a match, it updates the existing card-on-file to point at the newest processor reference instead of creating another record.

Why not include the expiry date in the match: it is not returned on the add-card path (it is stored masked), so it cannot be compared.

## 7. Testing

- `PayStaffActionsControllerTest`: 20 of 20 passing (ticket description).
- Checked by hand in the Partial Copy sandbox (2026-07-20): re-entering the same card no longer creates a duplicate.
- Whether a test fails without the fix is not recorded in the ticket.

## 8. Step by step

1. Query existing card-on-file records for the account with the same brand and last four digits.
2. If one exists, update its processor reference to the new one; otherwise create a new record.
3. Add a test that saves the same card twice with different processor references and asserts one record remains.

## 9. Rollback

Redeploy the previous version of `PayStaffActionsController`. Any duplicates created after a rollback would need merging by hand.

## 10. Known limits

- Two genuinely different cards on one account with the same brand and last four digits would be treated as one card. Not addressed in the ticket.
- Duplicates created before the fix are not cleaned up by it; whether any existed outside the sandbox is not recorded.
- Not in production until the DDT Pay cutover (DDT-249).

## 11. Reuse for similar issues

- Signs: duplicates appear even though a uniqueness check exists. Check whether the "unique" key is actually regenerated by an outside system each time.
- Match on stable business attributes (owner + brand + last four) when the external reference is not stable, and point the surviving record at the newest reference.
