## 1. Summary

The firm stopped using Salesforce Marketing Cloud and asked for its packages to be uninstalled. An uninstall is refused while anything of the firm's own still points at the package, so most of the work was finding and removing those references: a Lightning page component, seven page layouts, a report, eight Journey Builder flows and process builders, and a subflow call inside a core Opportunity flow. The Marketing Cloud data was backed up first, then the packages were uninstalled on 2026-08-28.

Two weeks later, DDT-990 found two record-triggered flows still setting a "sync to Marketing Cloud" flag on every Lead and Account save, costing a second save each time for a system that no longer existed. Both were deactivated on 2026-09-15.

## 2. What was reported

- **DDT-846 (2026-08-26).** Request to uninstall the Marketing Cloud packages, since the firm no longer subscribed to or used Marketing Cloud. Required a dependency check before the uninstall.
- **DDT-990 (2026-09-10).** Found while mapping automations for the DDT-825 backfill: `Clients_Sync_to_SFMC` (Account) and `Leads_Sync_to_SFMC` (Lead) were still active and writing `Sync_to_SFMC__c` on the triggering record. Against the backfill population alone, the Lead flow would have fired on **21,485 of 33,197 Leads** and the Account flow on **828 of 34,543 Accounts**.

Checking the premise of DDT-846: Marketing Cloud's last send was on **2026-08-18**. It had been sending 230 to 590 emails a day until then. Only the tracking sync (opens and clicks on old sends) was still active.

**Out of scope**

- **Replacing the email drips** that Marketing Cloud ran. Flagged for a business decision (see section 10).

## 4. How it works (background)

```
Record saved (Lead / Account / Opportunity / Contact)
  -> JBSystem_<Object>_Process (Process Builder, generated by Journey Builder)
       -> JBSystemFlow_<Object> (autolaunched flow)
            -> Marketing Cloud package action -> journey entry event
  -> Court_Case_After_Save_v3 (Opportunity)
       -> also called JBSystemFlow_Opportunity as a subflow
  -> Clients_Sync_to_SFMC / Leads_Sync_to_SFMC (after save)
       -> set Sync_to_SFMC__c on the same record = a second save
```

Journey Builder generates a **matched pair** per object: a Process Builder that is the record trigger, and an autolaunched flow that fires the event. Their version numbers pair exactly.

## 5. Root cause

Not a fault; this was a retirement. The findings that mattered:

1. **The packages could not be uninstalled while the firm's own components referenced them.** Production's dependency data (`MetadataComponentDependency`) listed the page, layouts, report and four `JBSystemFlow_*` flows.
2. **The flows could not be deleted by a metadata deploy.** Three check-only validations failed with only "insufficient access rights on cross-reference id", even for a flow that was already inactive, so deactivation was not the missing step. The first explanation (the packaged action inside the flow) was **wrong**. The Setup UI named the real blocker in one line: each flow was referenced by its matching `JBSystem_*_Process` Process Builder. Those had been written off as "legacy, not blockers".
3. **The dependency API missed a live caller.** `MetadataComponentDependency` has a blind spot for flow-to-subflow references, so it never reported that `Court_Case_After_Save_v3` called `JBSystemFlow_Opportunity` on every Opportunity save. It was found by searching the repo. After the uninstall, that core flow would have been calling a missing subflow.
4. **The sync flows (DDT-990)** are after-save flows that update their own record, with entry criteria that fire on **any** update of a matching record, not only on a change. Each firing is a full extra save, including another pass through every before-save trigger.

## 6. Solution

### 6.1 Clear the blockers (PR #255, deployed 2026-08-27)

Removed the Lightning page component, the Marketing Cloud sections from seven layouts (243 lines removed, none added), and deleted the report. The layout changes may not have been strict blockers, since Salesforce strips package fields from layouts on uninstall, but removing them explicitly is reviewable, while letting the uninstall rewrite seven layouts silently is not.

Before editing, every component was retrieved from production and compared with the repo. Two had drifted; they were committed as-is in a separate commit first, so the clean-up diff did not silently revert production changes.

This deploy contained no Apex, so no test level was passed.

### 6.2 Delete the Journey Builder flows (in Setup, recorded in PR #262)

The order that worked:

1. Delete the four `JBSystem_*_Process` Process Builders (the callers).
2. Activate a new version of `Court_Case_After_Save_v3` without the subflow call. The removed decision had one rule and one default that both led to the same next step, so it existed only to gate the Marketing Cloud call. The new start points straight at that step; every other element count is unchanged.
3. Delete `JBSystemFlow_Account`, `_Contact` and `_Lead`.
4. Deactivate, then delete, `JBSystemFlow_Opportunity`.

No paused flow interviews existed, so no in-flight work was orphaned. Copies of everything deleted were kept in the partial sandbox and compared against the production copies.

### 6.3 Back up, then uninstall (2026-08-28)

The uninstall destroys the package's data. The main email results object was exported first: **57,730 records**, matching the live count, with the file re-parsed to confirm row and Id counts. The planned uninstall order was `mktcloudlabs` (Journeys) first, then `et4ae5` (Marketing Cloud Connect), then `MCCA5PROD` (the connected app the other two sign in through). DDT-990 records Marketing Cloud Connect as uninstalled on 2026-08-28, with production's Apex class count going from 4,597 to 4,073. The exact sequence on the day is not recorded in the ticket.

### 6.4 Deactivate the sync flows (DDT-990, 2026-09-15, recorded in PR #393)

Both flows were deactivated in production. The repo was updated to match: the flow definitions show no active version, and the flow version files were retrieved from production showing `Obsolete`. **Both files had to change together**: a deploy of the flow file alone, still saying `Active`, would have created a new active version and silently undone the deactivation.

## 7. Testing

- **Custom code sweep:** all non-namespaced Apex classes (449), triggers (38), Visualforce pages (59), LWC and Aura files were exported and searched for the package namespaces. **0 hits.** A first attempt filtered `ApexClass.Body` in SOQL, which Salesforce rejects; its empty result nearly passed as "no matches". The source was exported and searched locally instead.
- **Consent data:** the Marketing Cloud mobile opt-out field was true on 0 Contacts, Leads and Person Accounts, so no consent records were lost.
- **Blocker deploy validation** against production with `RunLocalTests`: 9 of 9 components, 2,246 of 2,246 Apex tests passing.
- **After the flow deletions:** the dependency query returned only rows from the package's own flows, which leave with the package.
- **DDT-990:** both flow definitions show no active version. A dependency check on all three `Sync_to_SFMC__c` fields found no Apex, formula, validation rule, layout, list view, saved report or dashboard reading them.
- **2026-11-05:** no package licence record exists in production for any of the three namespaces.

**Not covered:** no test proves the uninstall left nothing behind beyond the checks above; the rehearsal in the partial sandbox was recommended in the review doc, and whether it was done first is not recorded.

## 8. Step by step

1. **Confirm the premise.** Check when the integration last actually did something (here, the last email send date), not when records were last created.
2. **List dependencies** with `MetadataComponentDependency` on the package namespace, then **also search the repo** for the namespace and for any flow calling the package's flows as subflows.
3. **Retrieve every component you will touch from production** and compare with the repo before editing.
4. **Deploy the page, layout and report changes**, with deletions in a post-destructive manifest so pages stop referencing objects before they are removed.
5. **Delete generated flows in Setup**, callers first (Process Builders), then fix any live flow that calls them, then the flows themselves.
6. **Export the package's data** and verify the export by re-reading it.
7. **Uninstall in dependency order**, the connected-app package last.
8. **Look for flows that still feed the retired system** (fields like "sync to X") and deactivate them.
9. **Record every Setup change in git** with a pull request the same day.

## 9. Rollback

- **Layouts, page and report:** redeployable from git history until the uninstall; the report cannot come back after it, because its report type no longer exists.
- **Deleted flows:** copies are kept in the partial sandbox.
- **The uninstall:** not reversible. The package data survives only in the export.
- **Sync flows:** reactivating a version in Setup restores them, but there is nothing for them to feed.

## 10. Known limits

- **Lost email programmes.** The licence-reinstatement drip, birthday emails and "trying to reach you" series all stopped on 2026-08-18. The review doc asked for confirmation that this was intended; the answer is not recorded in the ticket.
- **`Sync_to_SFMC__c` still exists** on Lead, Account and Opportunity, and `Court_Case_Sync_to_SFMC` still writes the Opportunity copy. Deleting them is pending a decision.
- **`Lead.Sync_to_SFMC__c` was not in git** when DDT-990 was filed. Add it to git before deleting it, so the deletion is recorded as a deletion.
- **One layout carries a one-line difference from production.** A platform-added action exclusion on the Person Account layout cannot be deployed back, so it was dropped from the repo copy.

## 11. Reuse for similar issues

**How to recognise one:** retiring any managed package, or flows that write a flag for an integration that has gone.

- **Trust the Setup UI's error over a deploy's.** "Insufficient access rights on cross-reference id" said nothing; the UI named the referencing process.
- **The dependency API misses subflow calls.** Search the repo for flow names too.
- **Generated automation comes in pairs.** Delete the caller before the callee.
- **Back up package data and verify the backup** before any uninstall.
- **After-save flows that update their own record** with criteria that do not require a change double every save. Look for these whenever an integration is retired.
- **Keep the flow definition and flow version files in step** when recording a deactivation in git.
